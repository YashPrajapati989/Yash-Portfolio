# 📜 Project Constitution

**Project Name:** Yash Portfolio

**Version:** 1.0

**Status:** Active

---

# Purpose

This document defines the non-negotiable principles, standards, architecture, and development philosophy for the Yash Portfolio project.

Every developer, AI assistant, or contributor working on this repository must follow this document before writing code.

This repository should be treated as a real-world software product rather than a simple portfolio website.

---

# Vision

Build one of the highest quality developer portfolio websites that demonstrates not only technical ability but also engineering discipline, storytelling, user experience, accessibility, performance, and software architecture.

The portfolio should feel like an immersive digital experience rather than a résumé.

# Development Philosophy

Build the portfolio exactly as a software company would build a production application.

No rushed development.

No unnecessary shortcuts.

No duplicate components.

No copy-paste architecture.

---

# Folder Structure

The project follows a modular architecture.

Each folder has a single responsibility.

Top-level folders should not be created unless absolutely necessary.

Any architectural change must be justified.

---

# Git Philosophy

Never commit directly to main.

Never develop directly on develop.

Every feature belongs to its own branch.

Every branch should represent one logical change.

Use Pull Requests for all merges.

---

# Commit Convention

Follow Conventional Commits.

Examples:

feat(hero): create hero layout

fix(nav): improve mobile navigation

docs(readme): update installation guide

style(button): improve hover animation

refactor(layout): simplify app layout

---

# Component Philosophy

Components must be:

Reusable

Composable

Small

Readable

Accessible

Documented

If a component becomes too large, split it.

---

# Styling Philosophy

Use design tokens.

Avoid hardcoded values.

Reuse spacing.

Reuse colors.

Reuse typography.

Maintain consistency.

---

# Animation Philosophy

Motion should guide attention.

Motion should never distract.

Animations must remain smooth.

Prefer subtle transitions.

Avoid excessive effects.

---

# Accessibility

Accessibility is mandatory.

Every feature must support:

Keyboard navigation

Focus visibility

Semantic HTML

ARIA labels

Screen readers

Proper color contrast

---

# Performance

Every feature should be evaluated for performance.

Prefer:

Server Components

Lazy Loading

Dynamic Imports

Optimized Images

Minimal JavaScript

Avoid unnecessary client-side rendering.

---

# SEO

Every page must include:

Metadata

OpenGraph

Twitter Cards

Structured Data

Canonical URLs

Robots.txt

Sitemap

---

# Documentation

Major architectural decisions should be documented.

The repository should remain understandable months after development.

If a decision requires explanation, create an ADR (Architecture Decision Record).

---

# AI Usage Policy

AI is an engineering assistant.

AI should explain architectural decisions.

AI should not generate unnecessary code.

AI should not modify project architecture without explanation.

If requirements are unclear, AI must ask questions instead of making assumptions.

---

# Definition of Done

A task is complete only if:

- Functionality works correctly.
- TypeScript has no errors.
- ESLint passes.
- Responsive layout verified.
- Accessibility reviewed.
- Performance considered.
- Documentation updated if necessary.
- Code reviewed.
- Commit created using Conventional Commits.

---

This portfolio should not only impress recruiters visually.
